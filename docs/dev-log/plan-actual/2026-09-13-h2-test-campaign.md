## Recurring-class candidates (for Rose, before wave 2)

1. **The routing-audit tool cannot see Workflow-internal dispatches by name.** `claude-routing-audit.py` folds all six wave-1 lanes into a generic "general-purpose" role; only the Workflow's own JSON shows they ran as `curie-validation-tester`, `rose-systems-auditor`, `noether-math-reviewer`, `pat-user-tester` ×2, `gauss-numerical-engineer` with the correct models. G12 is currently being satisfied or failed on evidence that does not actually cover the lanes it exists to check.
2. **Pre-plan recon dispatches keep tripping the same-day explicit-model check.** RECON ran before this campaign's routing discipline was locked in, yet it counts against the same calendar-date `--enforce` gate. Either exempt dated pre-plan recon from G12, or require it to carry an explicit model too — but the charter should say which, so this does not recur silently every wave.
3. **Mid-campaign `AGENT_LOG.md` entries go stale within hours.** The 2026-09-13 entry already misstates PR #326's state. A wave that runs mostly unattended will accumulate several such points before C1 gets to refresh them; consider a "measured as of HH:MM" convention instead of a static past-tense claim.
4. **Dual-named lenses collapse silently to one dispatched agent type.** L5's "Karpinski/Rose" roster entry produced a single `rose-systems-auditor` child with no record of why the other lens did not run. If a roster names two lenses, the dispatch or its receipt should say which one(s) actually ran.
5. **Multi-slice PRs are fine only when every combined slice has its own independent gate.** A2+B0 landed together in #326 without incident because G2 and G3 check them separately; a future combination without independently checkable gates could hide a partial failure inside an otherwise-green PR.
