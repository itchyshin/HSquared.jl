## Findings and required regressions

### W3-01 — high: standalone payload-v2 can silently mislabel pedigree covariance

At baseline, `_build_ainv_and_diag_from_block_pedigree` normalized pedigree rows before constructing `Ainv` (`src/bridge_payload_v2.jl:71–81`), but `_parse_one_block` retained caller-supplied `Z` and `ids` (`120–156`). `parse_payload_v2` checked dimensions only (`306–334`); it did not align block IDs with the normalized pedigree IDs. `_dispatch_fit` then passed the mismatched tuple to the animal fitter (`460–467`). This was an estimand error, not merely a label error.

No-fit reproduction on the original candidate, using `julia --compiled-modules=no --project=.`: a block with pedigree and `ids = ["calf", "sire", "dam"]`, `Z = I`, and parents of calf `sire`/`dam` parsed successfully. The returned block IDs remained `["calf", "sire", "dam"]`, while `normalize_pedigree` returned `["sire", "dam", "calf"]` and the returned precision used that latter order. The off-diagonal relationships were assigned to the wrong IDs (the self-relationships happen to be all one in this non-inbred fixture). Existing tests prove the normalization and Henderson inverse for the unsorted three-animal input (`test/runtests.jl:1379–1417`), but the payload-v2 tests use aligned order (`10690–10749`) and did not cross this mismatch.

**Fix after coordinator reassignment:** `src/bridge_payload_v2.jl:71–96` now validates the block IDs and permutes `Ainv` and `1 + F` into the supplied incidence-column order; already sorted order skips the permutation. Explicit v2 and the legacy alias pass their IDs to this builder (`149–156,375–400`). The legacy alias uses pedigree row IDs when its optional top-level `ids` are absent. The dedicated regression compares `Z * inv(Ainv) * Z'` with an independently permuted pedigree oracle, checks an inbred self-relationship, preserves the sorted route, and rejects missing/duplicate IDs (`test/wave3_payload_pedigree_order.jl:1–81`). It was RED at 2 pass/1 fail before the v2 fix, RED at 6 pass/1 fail on the legacy neighbor, and GREEN at 9/9 then 11/11 after both fixes. The coordinator will include this file from `test/runtests.jl`.

The current R FA/GLLVM bridge is outside the failure path: R topologically sorts pedigree rows and IDs (`R/model-spec.R:1263–1272,2375–2478`) before constructing `Z` (`R/bridge-payload.R:25–43`); FA calls `fit_multivariate_reml` directly (`R/julia-bridge.R:2819–2848`), while GLLVM checks Julia's normalized IDs before fitting (`R/julia-bridge.R:6017–6030`). A dedicated unsorted-pedigree R–Julia regression would strengthen this invariant, especially for FA, which does not repeat the explicit GLLVM ID check.

### W3-02 — medium: unwired-route error claims all fitting is unimplemented

At baseline, `Phase0NotImplementedError` printed “Model fitting is planned but not implemented yet” (`src/errors.jl:10–16`). `fit_payload_v2` used this type for the unwired multivariate and `coefcov` dispatches (`src/bridge_payload_v2.jl:522–529,542–546`), while fitted Julia routes were exported (`src/HSquared.jl:60–87`). The type was valid for the specific missing dispatch, but its global message was false and could misdirect an applied user. Required regression: check `sprint(showerror, Phase0NotImplementedError(...))` describes only the requested operation and points to the supported direct fitter where one exists; do not assert that all model fitting is absent. A no-fit probe reproduced the stale baseline text.

After this review, the coordinator changed the error text to say only the requested route is unavailable (`src/errors.jl:10–17`) and added a regression. That separate fix is not certified by this packet's focused test command.
