## 5. Compiler circularity and root selection

`check-after-task.R` separates report structure from `check_acceptance_ledger(root)`. Its main entry checks structure then recursively re-verifies all child/top ledgers. The bridge child's G4 currently invokes `closeout.py check` while V3 itself depends on after-task reports. That establishes a parent/child cycle. The recursion guard prevents infinite repetition; it does not prove that acceptance criteria were satisfied.

There is also a root-selection defect in the proposed use: shared `shinichi-brain/tools/closeout.py` derives its root from its own file location. Supplying an absolute candidate report does not make it validate the candidate's ledgers or evidence registry. Its standard command therefore cannot independently establish candidate-local closure as written. The candidate does not contain its own copy of this compiler.

Use a candidate-local wrapper with explicit candidate root. For the child report, call the structure function by sourcing the R checker, avoiding its main ledger discovery, then validate the report's referenced candidate artifacts separately. The brain's memory/golden-set requirements remain distinct receipts where applicable. Do not use a broad recursion-skip environment variable as evidence of candidate acceptance.

Recommended dependency order: report structure and artifact evidence; child G4 disposition; A2/E1 bounded judgments; V1/V2/V3 fresh receipt checks and final claim records; one integrated ledger re-verification; final after-task compiler result. No child's CHECK should call an integrated compiler that requires its own parent to be already passed.
